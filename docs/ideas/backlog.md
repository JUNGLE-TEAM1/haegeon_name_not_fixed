# Product Backlog

이 문서는 MVP 개발 범위에는 넣지 않지만, 제품 방향상 나중에 검토할 만한 아이디어를 보관합니다.

현재 MVP의 우선순위는 `docs/01-product-planning.md`와 `docs/ideas/ai-reflection-board-idea.md`에 정의된 회고/트러블슈팅 보드 흐름입니다. 아래 항목은 MVP 구현을 지연시키지 않는 선에서 Post-MVP 후보로만 다룹니다.

## 1) 개발자 학습 리마인드와 블로그 초안 생성

### 상태

- 우선순위: Backlog
- MVP 포함 여부: No
- 검토 시점: 기본 회고/트러블슈팅 CRUD, RAG, MCP, Agent 데모 흐름이 완성된 이후

### 아이디어 요약

개발자가 AI와 나눈 학습 대화, GitHub 작업 기록, 트러블슈팅 경험, 개인 메모를 모아 “오늘 내가 실제로 배운 개념”을 되짚고, 밀도 있는 학습 회고 또는 개발 블로그 초안으로 정리해주는 기능.

단순 개념 요약기가 아니라, 사용자의 실제 학습 흔적을 바탕으로 “왜 이 개념을 찾아봤는지”, “무엇을 오해했는지”, “어디에서 이해가 바뀌었는지”, “프로젝트에 어떻게 적용했는지”를 끌어내는 방향이 핵심이다.

### 문제의식

- 개발자는 요즘 개념 학습이나 문제 해결을 AI 대화로 많이 처리한다.
- 하지만 AI와 나눈 대화는 지나가면 다시 떠올리기 어렵고, 무엇을 배웠는지 정리되지 않는다.
- AI로 생성한 블로그 글은 종종 일반론 위주라 밀도가 낮고, 개인의 시행착오나 실제 코드 맥락이 부족하다.
- “사람이 쓴 것처럼”이라는 요구는 AI 탐지 우회가 아니라, 글에 개인적 맥락, 실패, 비교, 적용 경험, 남은 질문이 들어가야 한다는 의미로 해석한다.

### 가능한 사용자 가치

- 오늘 배운 개념을 다시 떠올릴 수 있다.
- AI에게 물어본 내용이 흩어지지 않고 학습 기록으로 남는다.
- 블로그 초안에 실제 프로젝트 맥락과 개인의 사고 흐름이 들어간다.
- 나중에 같은 개념을 다시 만났을 때 과거의 이해 과정까지 참고할 수 있다.

### 기능 후보

| 기능 | 설명 | AI 기술 연결 |
| --- | --- | --- |
| 학습 대화 리마인드 | AI에게 물어본 내용, 직접 저장한 Q&A, 회고 메모에서 오늘 배운 개념을 추출한다. | RAG |
| 개념 이해도 정리 | `몰랐던 것`, `헷갈렸던 것`, `이해가 바뀐 지점`, `아직 애매한 것`으로 정리한다. | Agent |
| GitHub 기반 학습 맥락 수집 | 오늘 커밋/PR/Issue를 가져와 이 개념을 왜 배우게 됐는지 연결한다. | MCP |
| 블로그 초안 생성 | 배운 개념을 개발자 블로그 글 형태로 작성한다. | LLM + Agent |
| 글 밀도 점검 | 글이 일반론에 머무는지, 내 경험/코드/실패/비교가 들어갔는지 검사한다. | Agent |
| 관련 과거 학습 연결 | 예전에 비슷하게 배운 개념이나 트러블슈팅 기록을 찾아 연결한다. | RAG |

### 좋은 글의 기준

블로그 초안에는 다음 요소가 들어가야 한다.

- 내가 왜 이 개념을 찾아봤는지
- 처음에 무엇을 오해했는지
- 어떤 예시나 코드에서 이해가 바뀌었는지
- 비슷한 개념과 어떻게 구분했는지
- 실제 프로젝트에서 어디에 적용했는지
- 아직 확신이 없는 부분은 무엇인지
- 다음에 다시 보면 도움이 될 체크포인트는 무엇인지

피해야 할 글:

- “OO는 매우 중요합니다” 같은 일반론
- 공식문서 수준의 얕은 재설명
- 내 프로젝트 맥락이 없는 개념 나열
- 코드 없이 말로만 설명하는 글
- 장점/단점만 표로 정리하고 끝나는 글
- 결론이 너무 깔끔해서 실제 학습 흔적이 없는 글

### Agent 질문 후보

블로그 초안을 바로 생성하지 않고, 먼저 다음 질문으로 밀도를 확보한다.

1. 이 개념을 왜 찾아보게 됐나요?
2. 처음에 헷갈렸던 지점은 뭐였나요?
3. 이해가 바뀐 순간이 있었나요?
4. 프로젝트 코드에서 어디에 적용했나요?
5. 비슷한 개념과 비교하면 어떤 차이가 있나요?
6. 아직 찜찜한 부분은 남아 있나요?

### 블로그 초안 구조 후보

```md
# [개념명]을 이해하게 된 과정

## 왜 이 개념을 찾아봤나

## 처음에 헷갈렸던 점

## 내가 이해한 핵심

## 예제로 다시 설명하기

## 내 프로젝트에서는 어디에 적용됐나

## 비슷한 개념과의 차이

## 아직 남은 질문

## 다음에 다시 볼 체크리스트
```

### MVP에서 제외하는 이유

- 현재 MVP의 핵심은 회고/트러블슈팅 기록을 작성하는 end-to-end 흐름이다.
- 학습 블로그 생성까지 포함하면 글쓰기 제품으로 범위가 넓어진다.
- ChatGPT/Gemini 대화 기록 import, 글 품질 평가, 블로그 편집 UX가 추가되면 2주 과제 범위를 초과할 가능성이 높다.
- 이 기능은 기존 MVP가 충분히 동작한 뒤에도 자연스럽게 확장할 수 있다.

### Post-MVP 전환 조건

아래 조건을 만족하면 이 기능을 다음 단계 후보로 올린다.

- 회고/트러블슈팅 글 CRUD가 안정적으로 동작한다.
- RAG로 과거 기록을 검색하고 근거를 표시할 수 있다.
- MCP로 GitHub 활동을 가져오는 흐름이 구현되어 있다.
- Agent가 질문을 제한된 횟수 안에서 수행하고 초안을 생성할 수 있다.
- 사용자가 저장한 학습/회고 기록이 충분히 쌓여 있다.

## 2) 커밋 기반 트러블슈팅 문서화

### 상태

- 우선순위: Backlog
- MVP 포함 여부: No
- 검토 시점: 기본 트러블슈팅 글 작성, GitHub MCP 조회, RAG 유사 기록 검색이 완성된 이후

### 아이디어 요약

문제가 발생한 커밋, 의심되는 변경점, 에러 증상, 해결 커밋을 연결해 트러블슈팅 문서를 작성하는 기능.

사용자가 “이 커밋 이후 문제가 생겼다”거나 “이 에러가 언제부터 발생했는지 모르겠다”고 입력하면, 시스템이 GitHub 커밋/PR/파일 변경 이력을 가져와 문제 발생 지점을 추정하고, 사용자가 검토한 뒤 트러블슈팅 기록으로 저장한다.

### 문제의식

- 트러블슈팅 기록은 보통 문제가 해결된 뒤에 작성하므로, 어떤 변경이 문제를 만들었는지 흐려지기 쉽다.
- 커밋 메시지와 실제 변경 파일은 GitHub에 남아 있지만, 에러 증상과 해결 과정은 별도로 정리되지 않는다.
- 나중에 같은 문제가 반복되어도 “어떤 커밋에서 시작됐고, 어떤 커밋에서 해결됐는지”를 다시 찾기 어렵다.

### 가능한 사용자 가치

- 문제 발생 커밋과 해결 커밋을 함께 기록할 수 있다.
- 에러 증상, 원인 후보, 의심 변경점, 실제 해결 방법을 한 문서에 남길 수 있다.
- 비슷한 문제가 다시 생겼을 때 과거 트러블슈팅 기록을 RAG로 찾아볼 수 있다.
- 발표나 회고에서 단순히 “해결했다”가 아니라 “어떤 변경이 문제였고 어떻게 추적했는지”를 설명할 수 있다.

### 기능 후보

| 기능 | 설명 | AI 기술 연결 |
| --- | --- | --- |
| 문제 커밋 등록 | 사용자가 의심 커밋, PR, 브랜치, 에러 메시지를 입력한다. | CRUD |
| GitHub 변경 이력 조회 | MCP로 커밋 diff, 변경 파일, PR 설명, Issue 링크를 가져온다. | MCP |
| 원인 후보 추정 | Agent가 에러 증상과 diff를 보고 의심 변경점을 정리한다. | Agent |
| 과거 유사 이슈 검색 | 비슷한 에러 메시지, 태그, 파일명을 가진 과거 기록을 찾는다. | RAG |
| 해결 커밋 연결 | 문제가 해결된 커밋이나 PR을 트러블슈팅 문서에 연결한다. | MCP + CRUD |
| 트러블슈팅 문서 생성 | 문제 상황, 발생 커밋, 원인 후보, 해결 커밋, 재발 방지를 구조화한다. | LLM + Agent |

### 트러블슈팅 문서 구조 후보

```md
# [문제명] 트러블슈팅 기록

## 1. 문제 상황

## 2. 에러 메시지 / 증상

## 3. 문제가 발견된 시점

## 4. 의심 커밋 / PR

## 5. 변경 파일과 주요 diff 요약

## 6. 원인 후보

## 7. 확인한 방법

## 8. 실제 원인

## 9. 해결 커밋 / PR

## 10. 재발 방지 체크리스트
```

### Agent 질문 후보

1. 문제가 처음 발견된 시점은 언제인가요?
2. 마지막으로 정상 동작하던 커밋이나 배포 지점이 있나요?
3. 에러 메시지나 재현 절차가 있나요?
4. 의심되는 파일이나 기능 영역이 있나요?
5. 해결 후 어떤 커밋 또는 PR에서 문제가 사라졌나요?
6. 같은 문제가 다시 생기지 않게 어떤 테스트나 체크를 추가할 수 있나요?

### MVP에서 제외하는 이유

- 현재 MVP의 트러블슈팅 기능은 사용자가 입력한 문제 해결 과정을 AI 인터뷰로 정리하는 데 집중한다.
- 커밋 diff 분석, 문제 발생 시점 추정, 해결 커밋 연결은 GitHub 연동 범위와 Agent 판단 범위를 크게 넓힌다.
- 잘못된 원인 추정이 나올 수 있으므로, 사용자 검토와 근거 표시 UX가 충분히 준비된 뒤 도입하는 것이 안전하다.

### Post-MVP 전환 조건

아래 조건을 만족하면 이 기능을 다음 단계 후보로 올린다.

- GitHub MCP로 커밋/PR/Issue를 안정적으로 조회할 수 있다.
- 트러블슈팅 글 타입과 태그/검색이 안정적으로 동작한다.
- RAG로 과거 유사 에러 기록을 검색할 수 있다.
- Agent가 근거 기록을 표시하면서 제한된 질문/도구 호출 안에서 초안을 생성할 수 있다.
- 사용자가 AI의 원인 추정을 승인/수정할 수 있는 UX가 마련되어 있다.

## 3) AI 상담/의사결정 대화 Import

### 상태

- 우선순위: High Backlog
- MVP 포함 여부: No
- 검토 시점: 기본 회고/트러블슈팅 저장, RAG 인덱싱, 외부 맥락 저장 구조가 완성된 이후

### 아이디어 요약

사용자가 ChatGPT, Gemini 등 AI와 나눈 고민 상담, 기술 판단, 의사결정 대화를 회고 보드에 가져와 저장하고, 요약/결정/근거를 구조화해 RAG 검색 대상으로 만드는 기능.

사용자가 AI와 깊게 논의한 내용이 해당 서비스의 채팅 내역 안에만 남으면, 나중에 “왜 그런 결정을 했는지”, “무엇을 근거로 판단했는지”, “어떤 대안을 버렸는지”를 다시 찾기 어렵다. 이 기능은 외부 AI 상담 기록을 회고 보드의 장기 기억으로 가져오는 역할을 한다.

### 문제의식

- 중요한 고민과 의사결정을 ChatGPT/Gemini와 논의하는 경우가 많다.
- 하지만 상담 기록이 외부 AI 서비스 안에만 남으면 회고/트러블슈팅 기록과 연결되지 않는다.
- 나중에 같은 고민이 반복되어도 과거에 어떤 관점으로 논의했고 어떤 결론을 냈는지 찾기 어렵다.
- 회고 보드에는 최종 결론만 남고, 실제 사고 과정과 근거가 누락될 수 있다.

### 가능한 사용자 가치

- GPT와 상담한 고민/의사결정 맥락을 잊지 않고 보존할 수 있다.
- 과거 상담 내용을 RAG로 찾아 현재 회고나 의사결정에 다시 연결할 수 있다.
- 어떤 결정을 무엇을 근거로 했는지 추적할 수 있다.
- AI와 논의한 내용이 단발성 채팅이 아니라 개인의 판단 기록으로 축적된다.

### 기능 후보

| 기능 | 설명 | AI 기술 연결 |
| --- | --- | --- |
| 상담 내용 수동 붙여넣기 | 사용자가 AI 대화 중 중요한 부분을 복사해 외부 맥락으로 저장한다. | CRUD + RAG |
| 공유 URL 저장 | ChatGPT/Gemini 공유 링크와 사용자 요약을 함께 저장한다. | CRUD |
| 공유 URL 내용 Import | 공유 URL의 공개 대화 내용을 가져와 구조화한다. 정책/기술 검토 후 도입한다. | MCP 또는 Backend Import + RAG |
| 대화 요약/구조화 | raw conversation에서 핵심 질문, 결정, 근거, 남은 질문을 추출한다. | LLM + Agent |
| RAG 인덱싱 | 상담 기록 요약과 핵심 판단을 embedding해 검색 대상으로 만든다. | RAG |
| 회고 작성 중 관련 상담 추천 | 현재 회고 주제와 관련된 과거 AI 상담 기록을 찾아 보여준다. | RAG + Agent |

```json
    "맡은 파트가 항상 내가 원하는 것과 일치하지는 않는다",
    "운에 성장량을 종속시키지 않기 위해 맡은 부분에서 성장 포인트를 찾아야 한다"
  ],
  "tags": ["MLFQS", "역할 배정", "성장 태도", "AI 상담"]
}
```

### 추천 구현 단계

1. 수동 붙여넣기
   - 사용자가 상담 내용 중 중요한 부분을 직접 붙여넣는다.
   - 가장 안전하고 구현 난이도가 낮다.
2. URL + 사용자 요약 저장
   - 공유 URL과 사용자가 작성한 요약/결론을 저장한다.
   - 자동 파싱 없이도 의사결정 링크를 보존할 수 있다.
3. 공유 URL 내용 Import
   - 공유 URL의 공개 페이지 내용을 읽어와 구조화한다.
   - 페이지 구조 변경, 접근 권한, 정책 리스크를 확인한 뒤 도입한다.
4. ChatGPT/Gemini export import
   - 사용자가 내보낸 대화 기록을 업로드해 날짜/주제별로 인덱싱한다.
   - 개인 정보 정제와 선택 import UX가 필요하다.

### 회고 작성 중 사용 예시

```text
사용자:
오늘 역할 배정 때문에 다시 의욕이 떨어졌어.

RAG:
과거 AI 상담 기록 중 "MLFQS 역할 배정에 대한 상담"을 찾음.

Agent:
예전에 비슷한 상황에서 "맡은 파트에서 성장 포인트를 찾고, 남는 시간에 Priority Donation을 따라잡는다"는 결론을 냈습니다.
이번 상황도 그때와 비슷한가요, 아니면 다른 점이 있나요?
```

### MVP에서 제외하는 이유

- 현재 MVP의 핵심은 회고/트러블슈팅 글 작성 흐름과 GitHub MCP/RAG/Agent 최소 연결이다.
- 공유 URL 자동 import는 페이지 구조 변경, 접근 권한, 정책 검토가 필요하다.
- AI 상담 기록은 민감한 개인 데이터일 수 있으므로 사용자 동의, 선택 저장, 삭제 UX가 필요하다.
- 대화 전체를 그대로 RAG에 넣으면 품질과 개인 정보 문제가 생길 수 있어 구조화/필터링 설계가 필요하다.

### Post-MVP 전환 조건

아래 조건을 만족하면 이 기능을 다음 단계 후보로 올린다.

- 외부 맥락 저장 모델이 준비되어 있다.
- RAG 인덱싱과 근거 기록 표시가 안정적으로 동작한다.
- 사용자가 저장할 대화 범위를 직접 선택할 수 있다.
- raw conversation, summary, decisions, evidence를 분리해 저장할 수 있다.
- 민감한 대화 내용을 삭제하거나 RAG 대상에서 제외할 수 있다.

# 01. Product Planning

이 문서는 `docs/brief/final-spec.md`의 과제 요구사항을 기준으로 작성한 MVP 기획 문서입니다.
현재 MVP는 완성형 AI 회고 플랫폼이 아니라 **개발자가 자기 경험을 구조화된 기록으로 바꾸는 최소 루프**에 집중합니다.

## 1) 프로젝트 개요

- 프로젝트명: `Dev Reflection Board` (가칭)
- 한 줄 설명: 개발자가 오늘 겪은 작업, 고민, 의사결정, 트러블슈팅을 짧게 입력하면 AI가 유형에 맞는 질문을 던지고, 답변을 검색 가능한 회고/트러블슈팅 기록으로 저장해주는 서비스
- 개발 맥락: 개인 과제 / 데모 중심 MVP
- 팀 구성: 솔로 개발
- 제출 목표: 전체 소스 코드와 발표용 `README.md`를 포함한 실행 가능한 웹 애플리케이션
- 관련 보조 문서:
  - 아이디어 원문: `docs/ideas/ai-reflection-board-idea.md`
  - 벤치마킹 조사: `docs/research/benchmark-services.md`
  - Post-MVP 백로그: `docs/ideas/backlog.md`
  - MCP Spike 결과: `docs/sprint/mcp-spike.md`

## 2) 문제 정의

개발자 또는 개발자 지망생은 프로젝트를 진행하면서 기술 문제, 의사결정, 감정적 흔들림, 팀 협업 이슈를 계속 겪는다. 하지만 이 경험은 보통 흩어진 채로 지나가고, 나중에 다시 쓸 수 있는 기록으로 남기 어렵다.

- 현재 불편함:
  - 빈 화면 앞에서 회고나 트러블슈팅 기록을 처음부터 쓰기 어렵다.
  - “오늘 무엇을 했는가”는 기억해도 “왜 그렇게 판단했는가”는 금방 흐려진다.
  - 에러 해결 과정은 지나고 나면 원인, 시도, 결론이 섞여 다시 찾기 어렵다.
  - AI와 나눈 고민이나 GitHub 작업 흔적이 회고 기록과 연결되지 않는다.
  - 과거에 비슷한 고민을 어떻게 정리했는지 다시 찾기 어렵다.
- 왜 지금 풀 가치가 있는가:
  - 이번 과제는 게시판 CRUD 위에 RAG, MCP, AI Agent를 실제 서비스 흐름으로 연결하는 것이 목표다.
  - 회고/트러블슈팅 기록은 과거 기록 검색(RAG), 외부 작업 맥락 수집(MCP), 질문 기반 정리(Agent)가 모두 자연스럽게 필요한 문제다.
- 기존 방식의 한계:
  - 일반 메모 앱은 사용자가 스스로 구조화해야 한다.
  - 단순 AI 요약은 사용자의 생각과 판단 과정을 충분히 끌어내지 못한다.
  - GitHub 커밋 목록만으로는 감정, 의사결정, 배운 점, 다음 행동을 설명하기 어렵다.

## 3) 타겟 사용자

- 핵심 사용자: 개발자 또는 개발자 지망생
- 구체 사용자: 개인 프로젝트, 팀 프로젝트, 학습 과제, 부트캠프, 실무 개발 과정에서 문제 해결과 회고를 기록하고 싶은 사람
- 사용 상황:
  - 하루 작업을 마치고 회고를 남길 때
  - 에러 해결 과정을 트러블슈팅 기록으로 남길 때
  - 기술 선택이나 구현 방향에 대한 의사결정을 정리할 때
  - 역할 배정, 팀 협업, 성장 욕구처럼 개발 과정에서 생긴 고민을 정리할 때
  - 예전에 비슷한 고민이나 문제를 어떻게 해결했는지 다시 찾고 싶을 때
- 사용 맥락: 데스크톱 웹 중심, 발표 데모에서는 하나의 기록 작성 루프를 end-to-end로 시연한다.

## 4) MVP 가치와 목표

MVP가 전달해야 하는 작은 가치는 다음이다.

> 개발자가 오늘 겪은 일이나 고민을 짧게 적으면, 서비스가 좋은 회고 질문을 던지고, 그 답변을 나중에 다시 찾을 수 있는 회고/트러블슈팅 기록으로 저장해준다.

### 제품 목표

- 사용자의 짧은 입력을 구조화된 회고/트러블슈팅 기록으로 바꾼다.
- 기록은 나중에 검색, 태그, 타입, 관련 기록으로 다시 찾을 수 있어야 한다.
- RAG/MCP/Agent는 완성형 고도화가 아니라, 이 기록 작성 루프를 강화하는 최소 단위로 포함한다.

### 사용자 경험 목표

- 사용자는 처음부터 완성된 글을 쓰지 않아도 된다.
- AI는 바로 글을 대신 쓰기보다 좋은 질문으로 맥락을 끌어낸다.
- 사용자는 AI가 만든 초안을 검토하고 수정한 뒤 저장한다.
- 저장된 기록은 “오늘 뭐 했다”가 아니라 사건, 판단, 배움, 다음 행동을 담는다.

### 기술 목표

- React 기반 프론트엔드를 구현한다.
- Next.js, NestJS, FastAPI, Spring Boot 중 하나 이상의 백엔드를 선택해 구현한다.
- PostgreSQL, MariaDB, MySQL 중 하나 이상의 관계형 DB를 사용한다.
- 상용 LLM을 연동한다.
- 게시판 필수 기능인 회원가입/로그인, 게시물 CRUD, 댓글, 태그, 페이징, 검색을 구현한다.
- RAG, MCP, AI Agent를 각각 최소 기능으로 구현하거나 실험 결과를 남긴다.

## 5) MVP 핵심 루프

MVP의 핵심은 아래 루프를 완성하는 것이다.

```text
짧은 입력
-> 회고 유형 선택 또는 분류
-> 유형별 질문
-> 답변 저장
-> 구조화된 초안 생성
-> 사용자가 수정
-> 검색 가능한 기록으로 저장
-> 나중에 검색/태그/관련 기록으로 다시 찾기
```

이번 MVP는 완벽한 조언자나 완성형 AI 플랫폼이 아니라, 이 루프가 실제로 동작하는 것을 목표로 한다.

## 7) 회고 유형과 질문 전략

모든 상황에 같은 질문을 던지지 않는다. MVP Agent는 먼저 기록 유형을 선택하거나 분류하고, 유형별 질문 전략을 사용한다.

| 유형 | 쓰는 상황 | 질문 방향 |
| --- | --- | --- |
| `daily` | 하루 작업 회고 | 사건, 막힌 점, 배운 점, 다음 행동 |
| `trouble` | 에러나 문제 해결 기록 | 증상, 원인 후보, 시도, 해결, 재발 방지 |
| `decision` | 기술 선택이나 구현 방향 결정 | 선택지, 기준, 버린 선택지, 검증 계획 |
| `team_issue` | 역할 배정, 협업, 동기 저하, 팀 커뮤니케이션 | 감정, 기대, 통제 가능한 것, 팀에 미치는 영향, 다음 행동 |
| `learning` | 새 개념 이해나 오개념 수정 | 처음 이해, 바뀐 이해, 프로젝트 적용, 남은 질문 |

좋은 회고 질문의 기준:

- 사용자가 놓친 관점을 보여준다.
- 감정을 판단하지 않고 이름 붙인다.
- 통제 가능한 것과 불가능한 것을 나눈다.
- 추상적인 깨달음을 다음 행동으로 바꾼다.
- 과거 기록과 현재 상황을 연결한다.
- 성급한 결론을 단정하지 않고 검토하게 한다.

## 8) AI 기능 범위

### 8.1 Agent

MVP의 Agent는 멘토나 상담가가 아니라 **인터뷰어 + 정리자 + 제한적인 관점 제안자**다.

포함 기능:

- 사용자의 첫 입력을 분석한다.
- 회고 유형을 선택하거나 추천한다.
- 사건, 감정, 판단, 배움, 다음 행동 중 부족한 정보를 찾는다.
- 유형별 질문 전략에 따라 다음 질문을 선택한다.
- 최대 3~5개 질문 안에서 인터뷰를 마친다.
- 사용자가 “그만 정리해줘”라고 요청하면 즉시 초안을 생성한다.
- 답변을 구조화된 초안으로 정리한다.

제한 조건:

- 단정적 조언을 하지 않는다.
- 민감한 감정/팀 갈등에 대해 훈계하지 않는다.
- “정답”보다 선택지와 판단 기준을 제안한다.
- 같은 유형의 질문을 반복하지 않는다.
- 정보가 부족하면 불완전한 초안으로 표시한다.

권장 상태 흐름:

```text
START
-> CLASSIFY_TYPE
-> EXTRACT_FACTS
-> DETECT_GAPS
-> SELECT_QUESTION_STRATEGY
-> ASK_ONE_QUESTION
-> UPDATE_STATE
-> SHOULD_CONTINUE?
-> GENERATE_STRUCTURED_DRAFT
-> SAVE_ENTRY
```

### 8.2 RAG

MVP의 RAG는 “과거의 나를 기억하는 장치” 역할을 한다.

포함 기능:

- 저장된 회고/트러블슈팅 글의 `title`, `raw_memo`, `final_content`, `tags`를 검색 대상으로 삼는다.
- 새 인터뷰 입력을 기준으로 관련 기록 top-k를 찾는다.
- 관련 과거 기록을 인터뷰 화면 또는 초안 화면에 표시한다.
- Agent 질문이나 초안 생성에 관련 기록을 참고 자료로 넣는다.

MVP 기준:

- 가능하면 embedding 기반 검색을 사용한다.
- 구현 부담이 크면 태그/키워드 검색 fallback부터 시작해도 된다.
- 중요한 것은 “과거 기록을 현재 회고에 연결한다”는 제품 경험이다.
- RAG 결과는 숨기지 않고 “참고한 기록”으로 사용자에게 보여준다.

### 8.3 MCP

MVP의 MCP는 “오늘 실제로 무엇을 했는지 가져오는 외부 맥락 수집기” 역할을 한다.

포함 기능:

- 작은 커스텀 MCP Server 구현 또는 최소 Spike 결과
- JSON-RPC 기반 요청/응답 처리
- GitHub API 연동
- GitHub token 환경변수 관리
- 오늘 커밋 조회
- 가능하면 PR/Issue 조회
- 가져온 활동을 인터뷰 세션의 외부 맥락으로 저장

MVP tool:

| Tool | 설명 |
| --- | --- |
| `get_today_github_activity` | 지정한 repository에서 오늘 커밋/PR/Issue 활동을 조회한다. |

MVP 기준:

- read-only tool을 우선 구현한다.
- 사용자가 어떤 외부 데이터를 가져왔는지 확인할 수 있게 한다.
- 실패 시 GitHub 맥락 없이도 인터뷰를 계속 진행할 수 있어야 한다.
- 실제 제품이라면 공식 GitHub MCP Server 사용도 고려할 수 있지만, 이번 과제에서는 MCP Server 구현 경험이 요구되므로 작은 커스텀 서버를 우선한다.

## 9) 핵심 사용자 흐름

### Flow A. 인터뷰 기반 기록 작성

1. 사용자는 로그인한다.
2. 사용자는 오늘 남기고 싶은 경험, 고민, 판단, 문제 해결 내용을 짧게 입력한다.
3. 시스템은 입력 내용을 바탕으로 기록 유형을 선택하거나 추천한다.
4. Agent는 유형에 맞는 질문을 3~5개 던진다.
5. 사용자는 답변한다.
6. 시스템은 답변을 구조화된 회고 초안으로 만든다.
7. 사용자는 초안을 수정한 뒤 저장한다.
8. 저장된 기록은 목록, 검색, 태그, 상세 화면에서 확인된다.

### Flow B. 트러블슈팅 기록 작성

1. 사용자는 에러 증상이나 해결한 문제를 입력하고 `trouble` 타입을 선택한다.
2. Agent는 증상, 원인 후보, 시도한 방법, 최종 해결, 재발 방지 항목 중 빠진 정보를 질문한다.
3. 시스템은 트러블슈팅 템플릿으로 초안을 생성한다.
4. 사용자는 수정 후 저장한다.
5. 이후 검색/태그/관련 기록으로 다시 찾아본다.

### Flow C. 관련 과거 기록과 GitHub 맥락 활용

1. 사용자가 회고 작성을 시작한다.
2. RAG는 과거의 관련 기록을 찾는다.
3. MCP는 오늘 GitHub 활동을 가져온다.
4. Agent는 관련 기록과 GitHub 활동을 참고해 더 구체적인 질문을 만든다.
5. 관련 기록과 GitHub 활동은 사용자에게 근거로 표시된다.

## 10) 성공 기준

## 12) 구현 순서

1. 앱 기본 실행 구조와 DB 연결
2. 인증 기초
3. 회고/트러블슈팅 글 CRUD
4. 태그, 검색, 페이징, 댓글
5. 회고 유형과 질문 템플릿
6. 인터뷰 세션과 답변 저장
7. LLM 초안 생성
8. 관련 과거 기록 추천(RAG 최소 구현 또는 fallback)
9. GitHub MCP Spike 또는 최소 tool 구현
10. Agent 질문 선택 최소 구현
11. 실패 처리, 제한 횟수, README 데모 정리

구현 원칙:

- 먼저 “질문 -> 답변 -> 초안 -> 저장” 루프를 완성한다.
- RAG/MCP/Agent는 이 루프 위에 작은 기능으로 붙인다.
- 처음부터 좋은 멘토나 완성형 Agent를 만들려고 하지 않는다.
- AI가 사용자의 원문과 학습/회고 흔적을 덮어쓰지 않게 한다.

## 13) 가정 및 오픈 질문

- [ ] 사용자 데이터는 개인별로 분리한다.
- [ ] AI 생성 결과는 사용자가 검토하고 수정한 뒤 저장한다.
- [ ] Agent는 인터뷰어/정리자 역할을 우선하고, 조언자는 제한적으로만 수행한다.
- [ ] RAG는 관련 과거 기록 추천부터 시작한다.
- [ ] MCP는 GitHub read-only 조회부터 시작한다.

- [ ] LLM과 Embedding 모델은 어떤 상용 모델을 사용할 것인가?
- [ ] Agent 구현은 직접 상태 머신으로 할 것인가, LangGraph 같은 구조를 사용할 것인가?
- [ ] GitHub MCP에서 커밋, PR, Issue 중 어디까지 MVP에 포함할 것인가?
- [ ] 댓글은 과제 필수 충족을 위한 최소 기능으로 둘지, 피드백 기능으로 확장할지 결정할 것인가?

## 14) Post-MVP 확장 방향

### Phase 1. 기록 작성 경험 강화

- 더 정교한 회고 유형 분류
- 유형별 질문 전략 고도화
- 반복 고민/반복 에러 패턴 요약
- 북마크, 중요 기록 고정

### Phase 2. 외부 사고 맥락 연결

- GPT 상담/의사결정 대화 Import
- ChatGPT/Gemini export/import
- 로컬 Markdown, TIL, 에러 로그 파일 연동
- 브라우저에서 사용자가 선택한 URL 저장

### Phase 3. 개발자 학습 기록 확장

- AI 대화 기반 학습 리마인드
- 배운 개념을 블로그 초안으로 정리
- 글 밀도 점검
- 관련 과거 학습 기록 연결

### Phase 4. 트러블슈팅 고도화

- 커밋 기반 문제 발생 지점 추정
- 해결 커밋 연결
- GitHub diff 기반 원인 후보 정리
- 재발 방지 체크리스트 생성

확장 원칙:

- MVP의 기록 작성 루프가 안정적으로 동작한 뒤 확장한다.
- AI 기능은 사용자의 원문, 판단, 수정 과정을 보존하는 방향으로 설계한다.
- 자동화가 사용자 데이터 수정 또는 외부 시스템 변경으로 이어질 경우 승인 단계를 둔다.
